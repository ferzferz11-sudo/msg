# Удаление сообщений v2 — поведение сервера

**Версия:** v1.3.0.31 | **Дата:** 2026-06-28

---

## Что изменилось

Сервер **полностью удаляет** записи из `messages_v2` при `DeleteMessageV2`. Пометка `content_type='deleted'` более не используется.

## Текущее поведение сервера

```
DeleteMessageV2(message_ids: ["id1", "id2"])
→ DELETE FROM messages_v2 WHERE id IN ('id1', 'id2')
→ success: true
```

Записи физически удаляются из БД. Нет "мусорных" записей с `content_type='deleted'`.

## Что нужно сделать клиента

### Android клиент

1. **Удаление сообщений** — ничего не меняется. Клиент вызывает `DeleteMessageV2` как раньше.

2. **Отображение удалённых сообщений** — если клиент показывает "Сообщение удалено" для записей с `content_type='deleted'`, это поведение больше не будет срабатывать (таких записей нет). Можно убрать проверку на `content_type == 'deleted'`.

3. **Оптимистичное удаление** — после вызова `DeleteMessageV2` сразу удаляйте сообщения из локального UI (как и раньше).

### Web клиент

То же самое — вызов `DeleteMessageV2` остаётся без изменений. Записи удаляются полностью.

## Что НЕ нужно

- Не нужно ловить `content_type='deleted'` — таких записей больше нет
- Не нужно показывать "Сообщение удалено" placeholder — сообщение просто исчезает из списка
- Не нужно проверять `text == '[deleted]'` —这样的 записей нет

## Миграция

Сервер уже очистил 8 "мусорных" записей. Клиентам не нужно делать миграцию — они просто перестают видеть удалённые сообщения.

## Откат

Если нужно откатить поведение — добавить в `DeleteMessageV2`:

```go
// Вместо DELETE — пометка
_, err = db.Exec(`UPDATE messages_v2 SET content_type = 'deleted', text = '' WHERE id = $1`, msgID)
```

Но это не рекомендуется — чистые удаления лучше для производительности.
