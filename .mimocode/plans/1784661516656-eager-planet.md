# Анализ Lavender Messenger v1.3.4.0 + Проектирование OIDC SSO

## Часть 1: Анализ текущей версии

### Сильные стороны

1. **Зрелая архитектура**: Чёткое разделение на домены (20+ файлов-хендлеров по domain-принципу). Каждый модуль (чаты, сообщения, профили, AI, компании, стикеры) изолирован.

2. **Безопасность (основная)**:
   - JWT access+refresh pair с device binding
   - Bcrypt cost 12
   - E2EE для секретных чатов (AES-256-GCM, ECDH key exchange)
   - Rate limiting: Redis-backed + in-memory fallback
   - gRPC interceptors блокируют неавторизованные вызовы
   - Panic recovery в stream-хендлерах
   - Graceful shutdown с broadcast `SERVER_SHUTTINGDOWN`

3. **Производительность**:
   - Cursor-based pagination (O(log n) вместо OFFSET)
   - Push notification batching (до 500 токенов за вызов)
   - Push debouncing (анти-спам)
   - Online presence O(1) через reverse-lookup sets
   - DB connection pool: 50 open / 25 idle
   - GIN index на `participant_ids[]` для быстрого поиска участников

4. **AI-система v2**: 9 провайдеров (OpenRouter, MiMo, Hermes ACP, Webhook, WebSocket, Subprocess, MCP, Reve, Local), 11 пресетов, marketplace с рейтингами, RAG pipeline (Qdrant + OpenAI embeddings), tool calling loop.

5. **Компании**: Полноценная multi-tenant система с иерархией позиций (Owner>TopManager>Manager>Employee), control доступа к чатам, invite codes, FCM push уведомления.

6. **Документация**: ARCHITECTURE.md, CLIENT_INTEGRATION.md, CHANGELOG.md с 80+ записями, doc/ с 12 файлами.

7. **Тесты**: ~88 тестов, включая интеграционные (ChatV2), auth, reactions, stability, company.

### Слабые стороны

**Критические (безопасность)**:

1. **HTTP middleware не проверяет тип токена** (`http_server.go:80-88`): `requireAuth` пропускает refresh tokens (30-дневные) к upload-эндпоинтам и TURN credentials. ГRPC interceptor проверяет `claims.Type == "access"`, но HTTP — нет.

2. **Нет issuer/audience claims в JWT**: `authClaims` не устанавливает `Issuer`/`Audience` из `RegisteredClaims`. Токен, выданный для одного сервиса, может быть использован против другого.

3. **Agent JWT — ручная реализация** (`auth/jwt.go`): Не использует `golang-jwt/v5`. `RevokeToken` — заглушка (no-op). Компрометированный agent-токен живёт 24ч без возможности отзыва.

4. **CORS `*`**: Для auth/upload сервера — любая страница может делать authenticated requests.

**Высокие**:

5. **Rate limiter без eviction**: `ipRateLimiter` хранит timestamp в `map[string][]time.Time` без cleanup-горутины. Под нагрузкой — unbounded memory growth.

6. **Access token не отзываем**: 15 минут без mechanism отмены. Смена пароля не аннулирует выданные access tokens.

7. **30-дневный refresh token**: Долго для lost device. В связке с HTTP middleware багом — кража refresh = доступ к HTTP API на 30 дней.

8. **`SignOut` не требует аутентификации**: Извлекает identity только из refresh token в body. Любой, кто знает refresh token, может деавторизовать device.

**Средние**:

9. **IP не сохраняется**: `signInV2` хардкодит `"unknown"` вместо реального IP (TODO в коде).

10. **`user_agent` = `clientVersion`**: Не настоящий HTTP User-Agent.

11. **In-memory rate limiter**: Нет распределённого rate limiting для multi-instance деплоя.

12. **Двух- Identity система**: Кодовая база мигрирует с username на UUID. У каждой DB-функции есть варианты `ByUserID` и по username — дублирование.

13. **README отстаёт от кода**: README.md ссылается на v1.1.2.4, реальная версия 1.3.4.0.

14. **`MigrateDeviceTables` не проверяет ошибки миграций**: Отдельные `db.Exec()` молча игнорируют ошибки.

15. **Диск переполнен на prod** (устранено): PostgreSQL PANIC из-за `No space left on device`. journal логи (2.2G) + coturn (706M) заполнили диск.

## Часть 2: Проектирование OIDC SSO-системы

### Концепция

Лава становится **OpenID Connect Provider**. Новые приложения (Android Kotlin + Web React/Next.js) аутентифицируют пользователей через Lavender credentials. Два режима входа:
- **SSO**: Lavender установлена → автоматический вход через существующую сессию
- **Credentials**: Lavender не установлена → форма логина → OIDC authorize flow

### Архитектура

```
┌─────────────────────┐     ┌──────────────────────────┐
│  Lavender Messenger │     │  Relying Party (RP)      │
│  (OIDC Provider)    │◄────│  - Android Kotlin App     │
│                     │     │  - React/Next.js Web App  │
│  Internal:          │     │  - Будущие приложения     │
│  - HS256 JWT        │     └──────────────────────────┘
│  - Device mgmt      │
│  - Rate limiting    │     ┌──────────────────────────┐
│                     │────►│  Lavender App             │
│  OIDC Layer:        │     │  (существующее приложение)│
│  - RS256 JWT        │     │  SSO через Intent/DL     │
│  - Auth codes       │     └──────────────────────────┘
│  - Client mgmt      │
│  - PKCE             │
└─────────────────────┘
```

**Ключевое**: OIDC-слой — **аддитивный HTTP API**. Никаких изменений в proto, gRPC interceptors, или существующие auth-таблицы.

### Стратегия токенов

| Тип токена | Алгоритм | Audience | Время жизни | Назначение |
|---|---|---|---|---|
| Internal Lavender JWT | HS256 | Lavender server | 15мин / 30д | Существующая auth (без изменений) |
| OIDC Access Token | RS256 | client_id | 1 час | Доступ к API RP |
| OIDC ID Token | RS256 | client_id | 1 час | Assertion личности |
| OIDC Refresh Token | opaque | client_id | 30 дней | Обновление токенов |
| Auth Code | opaque | N/A | 10 мин | One-time code exchange |

### SSO Flow (Android)

```
New App                    Lavender App              Lavender Server
   │                            │                          │
   │ 1. Check Lavender          │                          │
   │    packageManager          │                          │
   │──────────────────────►     │                          │
   │                            │                          │
   │ 2. Send SSO Intent         │                          │
   │    (client_id, PKCE,       │                          │
   │     state, redirect_uri)   │                          │
   │──────────────────────►     │                          │
   │                            │ 3. Validate local JWT    │
   │                            │                          │
   │                            │ 4. POST /oidc/sso-exchange│
   │                            │─────────────────────────►│
   │                            │                          │
   │                            │ 5. Validate JWT,         │
   │                            │    generate auth code    │
   │                            │◄─────────────────────────│
   │                            │                          │
   │ 6. Return auth_code        │                          │
   │◄──────────────────────     │                          │
   │                            │                          │
   │ 7. POST /oidc/token        │                          │
   │──────────────────────────────────────────────────────►│
   │                            │                          │
   │ 8. OIDC tokens             │                          │
   │◄──────────────────────────────────────────────────────│
```

**Fallback**: Если Lavender не установлена / Intent timeout / пользователь не залогинен → credential mode (форма логина → OIDC authorize).

### SSO Flow (Web)

1. RP redirect → `/oidc/sso-check` с OIDC параметрами
2. Lavender проверяет активную сессию (cookie/token)
3. Если сессия есть → генерирует auth code → redirect обратно к RP
4. Если нет → показывает страницу логина Lavender → после логина → auth code

### RS256 Key Management

Ключи генерируются при первом запуске:
```
.keys/oidc-private.pem   (RS256 signing)
.keys/oidc-public.pem    (served via JWKS)
.keys/oidc-kid           (key ID, UUID)
```
Ротация: генерируем новую пару → публикуем обе в JWKS 48ч → удаляем старую.

### Новые PostgreSQL таблицы

**`oauth_clients`** — OAuth2 клиенты (public/confidential):
- `client_id` (UUID), `client_secret_hash` (bcrypt), `client_name`, `client_type`
- `redirect_uris` (JSONB), `allowed_scopes` (TEXT[]), `allowed_sso` (bool)
- `is_active`, `created_at`, `updated_at`

**`oauth_refresh_tokens`** — Refresh tokens:
- `token_hash` (SHA-256), `user_id` (FK→users), `client_id` (FK→oauth_clients)
- `scope`, `is_revoked`, `expires_at`, `replaced_by_id` (rotation chain)

**`oauth_grants`** — User consent:
- `user_id` + `client_id` (composite unique), `scope`, `granted_at`

**`oauth_auth_codes`** — Audit trail (codes в Redis):
- `code_hash`, `user_id`, `client_id`, `code_challenge`, `is_used`, `is_sso`

**`oauth_access_tokens`** — Audit (AT — stateless JWT):
- `jti`, `user_id`, `client_id`, `scope`, `is_revoked`

**Изменений в существующие таблицы: НЕТ.**

### Security highlights

- **PKCE mandatory** (S256 only, plain rejected)
- **Separate signing keys**: HS256 (internal) ≠ RS256 (OIDC) — компрометация одной не влияет на другую
- **Refresh token rotation** с atomic SQL UPDATE (WHERE is_revoked = FALSE)
- **Token replay protection**: повторное использование auth code → отзыв всех токенов
- **Redirect URI**: exact string match, без wildcard
- **Client secrets**: bcrypt hash, показываются один раз при регистрации
